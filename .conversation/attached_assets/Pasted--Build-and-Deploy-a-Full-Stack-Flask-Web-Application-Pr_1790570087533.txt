# Build and Deploy a Full-Stack Flask Web Application

## Project Title

**QC-TaskManagerapp**

You are an expert full-stack software developer. Build a complete, functional, production-ready web application called **QC-TaskManagerapp** and deploy it as a live web application.

Do not create only a UI prototype. The application must have a working Flask backend, SQLite database, task scheduling, background job queue/cache, CRUD operations, browser reminders, dashboard statistics, HTTP status/response monitoring, and live deployment.

---

# 1. Technology Stack

Use only the following main technologies:

* **Frontend:** HTML5, CSS3, Bootstrap 5, JavaScript
* **Backend:** Python 3 + Flask
* **Database:** SQLite3
* **Task Scheduling / Background Jobs:** Python background worker with a reliable job queue/scheduler
* **Caching:** In-memory cache or SQLite-backed lightweight cache where appropriate
* **Templates:** Jinja2
* **Deployment:** Replit deployment

Keep the project simple and suitable for running on Replit.

---

# 2. Main Objective

QC-TaskManagerapp is a task scheduling and management web application.

Users should be able to:

1. Add a task with:

   * Task name/description
   * Date
   * Time

2. Schedule the task.

3. Store the task permanently in SQLite.

4. Automatically place scheduled tasks into a background job queue.

5. When the scheduled date and time is reached:

   * The background worker detects the task.
   * The task status changes to **Completed** or **Due**, depending on the implementation.
   * A browser popup/notification reminder is shown to the user when the web application is open.
   * The task should be clearly highlighted on the dashboard.

6. Users should be able to:

   * View tasks
   * Edit tasks
   * Update tasks
   * Reschedule tasks
   * Delete tasks
   * Mark tasks as completed
   * View upcoming tasks
   * View completed tasks

### Step 2 — Queue the Scheduled Task

After saving the task:

* Calculate the scheduled datetime.
* Add the task to the background job queue.
* The worker should continuously check upcoming scheduled tasks.
* Avoid creating duplicate queue jobs for the same task.
* If a task is edited or rescheduled, update its scheduled job accordingly.

The queue must work without blocking Flask request handling.

# 8. Background Job Queue

Implement a lightweight background task scheduler.

The architecture should be approximately:

```
             ┌────────────────────┐
             │   Flask Web App     │
             └─────────┬──────────┘
                       │
                       ▼
             ┌────────────────────┐
             │    SQLite DB       │
             │      Tasks         │
             └─────────┬──────────┘
                       │
                       ▼
             ┌────────────────────┐
             │   Job Scheduler    │
             │   / Background     │
             │      Worker        │
             └─────────┬──────────┘
                       │
                       ▼
             ┌────────────────────┐
             │ Scheduled Task     │
             │      Trigger       │
             └─────────┬──────────┘
                       │
                       ▼
             ┌────────────────────┐
             │ Reminder / Status  │
             │      Update        │
             └────────────────────┘
```

The worker must not block normal Flask requests.

Use a simple reliable scheduling approach suitable for Replit.

If using APScheduler or another lightweight Python scheduler, configure it correctly and explain the dependency in `requirements.txt`.

The cache should help avoid unnecessary repeated database queries.

Cache items may include:

* Dashboard task counts
* Upcoming tasks
* Recent task list

Invalidate or refresh the cache whenever:

* A task is added.
* A task is edited.
* A task is deleted.
* A task is completed.

Do not allow stale cache data to cause incorrect task reminders.

# 10. Live HTTP Status and Responses

The application must provide clear HTTP responses.

Implement appropriate status codes such as:

* `200 OK` — successful page/API request
* `201 Created` — task successfully created
* `400 Bad Request` — invalid task input
* `404 Not Found` — task does not exist
* `500 Internal Server Error` — unexpected server error

Create JSON API endpoints where appropriate.

For example:

```
GET    /api/tasks
GET    /api/tasks/<id>
POST   /api/tasks
PUT    /api/tasks/<id>
DELETE /api/tasks/<id>
```

Return JSON such as:

```json
{
  "success": true,
  "message": "Task created successfully",
  "task_id": 1
}
```

# 14. Database Design

Create SQLite database automatically when the application starts.

Use a `tasks` table similar to:

```sql
CREATE TABLE tasks (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    scheduled_date TEXT NOT NULL,
    scheduled_time TEXT NOT NULL,
    scheduled_datetime TEXT NOT NULL,
    status TEXT DEFAULT 'Scheduled',
    created_at TEXT NOT NULL,
    updated_at TEXT,
    completed_at TEXT
);
```

Add indexes where useful.

Use parameterized SQL queries to avoid SQL injection.
